## 前言

在使用 Astro Paper 主题时，我们可能需要从原作者那里更新主题以获取新功能。本文将详细介绍如何安全地更新主题并处理可能出现的冲突。这篇教程基于实际操作经验，会详细说明每个步骤可能遇到的问题。

## 当前代码架构总览

在动手合并之前，先搞清楚"哪些文件是谁的"，这是避免冲突的关键。当前项目（AstroPaper v7.2.0 架构）的目录职责如下：

```
src/
├── custom/            ← 🟢 你的地盘（v7.2.0 新增，上游承诺永不修改）
│   ├── Head.astro         渲染在每页 </head> 前：统计脚本、验证 meta
│   ├── BodyEnd.astro      渲染在每页 </body> 前：脚本、挂件
│   └── PostEnd.astro      渲染在文章末尾：评论、订阅表单（可拿到 post）
├── content/
│   └── posts/         ← 🟢 你的地盘：所有博客文章（Markdown）
├── components/        ← 🔵 主题组件（升级时可能被覆盖）
├── layouts/           ← 🔵 主题布局：Layout.astro 全站骨架、PostLayout.astro
├── pages/             ← 🔵 主题页面（路由）+ 少量你的文件
│   ├── index.astro        首页（我改过问候语和中文名言）
│   ├── about.astro        关于页（你的个性化内容）
│   ├── posts/[...slug]/   文章详情页
│   └── *.xml.ts / .txt.ts RSS、sitemap、robots.txt 等端点
├── styles/            ← 🔵 全局样式（global.css、typography.css）
├── utils/             ← 🔵 工具函数（日期、排序、slug 等）
├── config.ts          ← 🔵 站点配置（被 astro-paper.config.ts 覆盖）
└── content.config.ts  ← 🔵 文章 frontmatter 的 schema 校验
```

配置文件是 `astro-paper.config.ts`（站点标题、功能开关、社交链接都在这里改），依赖在 `package.json`，Astro 本身的配置在 `astro.config.ts`（Markdown 插件、Shiki 高亮等）。

**用颜色区分所有权**：🟢 绿色目录是你的内容，上游更新永远不会碰它；🔵 蓝色目录属于主题作者，`git merge` 时如果两边都改过同一个文件，就可能冲突。所以**自定义优先放绿色区域**（`src/custom/`、`src/content/`），迫不得已才改蓝色区域。

## 更新步骤

### 1. 创建备份分支

首先，创建一个备份分支来处理更新，这样可以保证主分支的安全：

```bash
git checkout -b backup
```

### 2. 添加上游仓库

如果还没有添加过原作者的仓库作为上游：

```bash
git remote add upstream https://github.com/satnaing/astro-paper.git
```

### 3. 获取上游更新

```bash
git fetch upstream
```

### 4. 合并上游更新

```bash
git merge upstream/main --squash --allow-unrelated-histories
```

这时会遇到冲突，通常会看到类似这样的提示：

```bash
CONFLICT (content): Merge conflict in src/content/posts/xxx.md
CONFLICT (content): Merge conflict in astro-paper.config.ts
CONFLICT (content): Merge conflict in pnpm-lock.yaml
```

### 5. 处理冲突

在处理冲突时，需要根据文件的不同类型采取不同的策略：

#### 5.1 处理文章冲突（/src/content/posts/）

对于博客文章目录下的冲突，通常我们要保留自己的文章：

1. 因为这些是你自己写的内容，不需要合并原作者的示例文章
2. 可以直接使用以下命令保留自己的所有文章：

```bash
git checkout --ours src/content/posts/* && git add src/content/posts/
```

#### 5.2 处理配置文件冲突

对于 `astro-paper.config.ts` 这样的配置文件：

1. 需要手动检查冲突
2. 保留自己的个性化设置（如语言、时区等）：
   ```typescript
   lang: "zh-CN", // 保留中文设置
   timezone: "Asia/Shanghai", // 保留中国时区
   ```
3. 同时也要合并原作者的新功能配置

#### 5.3 处理依赖相关文件

对于 `pnpm-lock.yaml`：

1. 通常可以直接使用自己的版本：
   ```bash
   git checkout --ours pnpm-lock.yaml && git add pnpm-lock.yaml
   ```
2. 原因是：
   - 这个文件是自动生成的，不需要手动合并
   - 之后运行 `pnpm install` 会自动更新到正确的状态

#### 5.4 其他文件冲突

1. `README.md`：通常保留原作者的版本，因为包含主题的重要信息
2. `.gitignore`：需要合并双方的规则，确保都生效
3. 样式文件：需要仔细对比，保留自己的自定义样式，同时合并新功能样式

### 6. 测试更新

在 backup 分支上测试更新是否成功：

```bash
pnpm install
pnpm run dev
```

关于 `pnpm install`：

1. 如果你在 backup 分支上已经运行过 `pnpm install`：
   - 切换到 main 分支后通常不需要重新安装
   - 因为 `node_modules` 目录是所有分支共用的
   - 依赖关系已经在 backup 分支更新好了
2. 但如果遇到以下情况，需要重新运行 `pnpm install`：
   - 出现模块找不到的错误
   - 原作者添加了新的依赖
   - `package.json` 有变动

### 7. 合并回主分支

测试无误后，将更新合并回主分支：

```bash
git checkout main
git merge backup
```

注意：

1. 这步通常不会有新的冲突
2. 因为所有冲突都在 backup 分支解决过了
3. 如果出现冲突，说明 main 分支在此期间有了新的改动

### 8. 推送更新

```bash
git push
```

### 9. 清理工作

完成后可以删除备份分支：

```bash
git branch -d backup
```

## 常见问题

### Q1: 为什么要创建备份分支？

A1: 备份分支可以让我们安全地处理冲突，如果出现问题可以随时回退，不会影响主分支。

### Q2: 合并后需要重新安装依赖吗？

A2: 通常不需要，因为：

1. `node_modules` 是所有分支共用的
2. 在 backup 分支处理冲突时已经更新过依赖
3. 合并到 main 分支不会影响依赖的安装状态

### Q3: 如何处理特定文件的冲突？

A3:

- 使用 `git checkout --ours 文件路径` 保留自己的版本
- 使用 `git checkout --theirs 文件路径` 使用上游版本
- 对于配置文件，最好手动合并以保留双方的重要改动

### Q4: 合并时遇到 "refusing to merge unrelated histories" 怎么办？

A4: 添加 `--allow-unrelated-histories` 参数即可，这在我们的命令中已经包含了。

## 注意事项

1. 更新前先确保本地改动已提交或暂存
2. 重要的配置文件一定要手动检查冲突
3. 合并后要完整测试网站功能
4. 保持良好的备份习惯
5. 记录自己对主题的修改，方便下次更新时参考

## 合并上游与自定义代码的注意事项

> 这一节是 2026-11-16 同步上游 v7.2.0 之后补充的实战经验，核心思想：**让上游更新的文件和自己的修改文件永远不相交，冲突就不会发生**。

### 1. 自定义代码放哪里

按优先级选择：

1. **`src/custom/` 官方插槽**（首选）—— v7.2.0 起提供，上游承诺永不修改这三个文件：
   - 统计脚本、验证 meta、额外样式 → `Head.astro`
   - 全站脚本、挂件 → `BodyEnd.astro`
   - 评论、订阅表单等文章尾部内容 → `PostEnd.astro`
2. **`astro-paper.config.ts` 配置** —— 功能开关、社交链接、站点信息，上游一般不会大改结构
3. **`src/content/` 内容** —— 文章、页面内容，天然是你的地盘
4. **直接改主题文件**（最后手段）—— 比如 `index.astro` 首页、`Layout.astro`。改之前想清楚：上游更新这个文件时，你必须手动合并

### 2. 如果必须改主题文件，做好记录

维护一份"修改清单"（可以记在文章里或 README），升级前对照检查。我目前的清单：

| 文件 | 修改内容 |
|---|---|
| `src/layouts/Layout.astro` | 注释掉 `<Font>`（Google Fonts 国内不可用） |
| `src/pages/index.astro` | 问候语改 `Hi, I'm Aimer`，英文介绍换中文名言 |
| `src/pages/posts/[...slug]/index.astro` | 加 `<Comments />`（Giscus） |
| `astro-paper.config.ts` | `dynamicOgImage: false`、Giscus 开启等 |

### 3. 合并上游前先做"代码对比"

不要盲合并，先看清楚上游改了什么：

- **GitHub compare 页面**：`https://github.com/satnaing/astro-paper/compare/v旧版本...v新版本` 看文件级 diff
- **GitHub API**：`https://api.github.com/repos/satnaing/astro-paper/compare/...` 拿精确的文件清单和增删行数（页面渲染失败时用它）
- **Release Notes**：重点看 breaking changes（比如 v7.2.0 说明 mdx 8 不允许再传 `remarkPlugins` 参数）

确认改动范围后，就能预判哪些文件会冲突、自己哪些修改要保留。

### 4. 依赖升级的坑

- **Windows 下先停掉 dev server 再 `pnpm update`**，否则 `node_modules` 文件被占用，会报 `ERR_PNPM_SYMLINK_FAILED`。报错了不要慌，重新执行一次即可，包已经下载好了
- **升级中断可能留下状态锁**：如果依赖安装中途被取消，后续安装可能报 `state lock timeout`，此时等锁过期后删掉 `node_modules` 全新安装最可靠
- **精确锁版本的依赖 `pnpm update` 不会动**：如果 package.json 里写的是 `"prettier": "3.9.10"`（没有 `^`），要升级必须显式 `pnpm add -D prettier@<新版本>`
- **lock 文件冲突**直接用自己的版本（`git checkout --ours pnpm-lock.yaml`），然后 `pnpm install` 重新生成
- **大版本依赖升级**（如 mdx 7 → 8）要读 release notes 检查自己的用法；我们的 `astro.config.ts` 是无参调用 `mdx()`，所以不受影响

### 5. 合并后的验证清单

```bash
pnpm install        # 依赖对齐
pnpm build          # 类型检查 + 全量构建 + pagefind 索引，一条命令验证所有
```

重点看：构建是否 0 错误、页面数量是否和预期一致、`astro check` 有没有新提示。

### 6. 一个反直觉的事实

冲突多少和你自定义的**多少**无关，和你自定义的**位置**有关。改 10 个主题文件不如用 1 个官方插槽；`src/custom/` 里写再多代码，上游更新也是零冲突。所以每次想加功能时，先问一句：官方插槽能不能装下？

## 结语

通过这种方式更新主题，可以既获得原作者的更新，又保留自己的修改。记住要经常备份，小心处理冲突，这样就能安全地完成更新。本教程中的所有步骤都是经过实际操作验证的，希望能帮助你顺利完成主题更新。
